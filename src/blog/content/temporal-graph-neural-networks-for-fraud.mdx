Fraud is a **temporal** phenomenon. A ring of mule accounts looks completely normal
in a static snapshot — the signal is in the *order* and *timing* of the edges they
create. A vanilla GraphSAGE model trained on daily snapshots simply cannot see that.

## The failure of snapshot models

We aggregated transactions into daily graphs and trained a 2-layer GraphSAGE
classifier. It hit **0.71 AUC** and, more importantly, its recall on
*coordinated* fraud (3+ accounts acting together within an hour) was only **22%**.
By the time a ring showed up in a daily aggregate, the money was gone.

## Temporal Graph Networks

A [TGN](https://arxiv.org/abs/2006.10637) keeps a **memory vector** per node that is
updated every time an edge touches it. Each interaction runs through:

1. a **message function** that builds a message from the two nodes' memories, the
   edge features, and the elapsed time since each node's last update;
2. a **memory updater** (a GRU) that folds the message into the node's memory;
3. an **embedding module** (temporal attention) that produces the representation
   used for the downstream classifier.

```python
class TGNMemory(nn.Module):
    def __init__(self, n_nodes, mem_dim, msg_dim):
        super().__init__()
        self.memory = nn.Parameter(torch.zeros(n_nodes, mem_dim), requires_grad=False)
        self.last_update = nn.Parameter(torch.zeros(n_nodes), requires_grad=False)
        self.gru = nn.GRUCell(msg_dim, mem_dim)

    def update(self, node_ids, messages, t):
        prev = self.memory[node_ids]
        self.memory[node_ids] = self.gru(messages, prev)
        self.last_update[node_ids] = t
```

The time encoding is what makes it work — `Δt` between a node's last event and the
current one is projected with a learnable Fourier basis, so "two transfers 5 seconds
apart" and "two transfers 5 days apart" produce very different messages.

<Callout type="warn" title="Leakage watch-out">
Memory makes temporal leakage easy to introduce. Process events in strict
timestamp order, update memory **after** you've computed the loss for that batch,
and never let a validation event update memory that a training event will read.
</Callout>

## Results

Same features, same false-positive budget (1.5%):

| Model | AUC | Recall @ coordinated fraud |
| --- | --- | --- |
| GraphSAGE (daily snapshots) | 0.71 | 22% |
| GAT (daily snapshots) | 0.74 | 29% |
| **TGN + memory** | **0.89** | **67%** |

3x the coordinated-attack recall, and detections landed a median of **41 minutes
earlier** because the model reacts to the *first* suspicious edge instead of waiting
for an aggregate.

## Keeping it explainable

Regulators need a reason, not a score. For every flagged account we surface:

- the **attention weights** over its recent neighbours (which counterparties drove the score)
- a **counterfactual** — the smallest set of recent edges that, if removed, flips the decision
- the memory-state delta that crossed the threshold

## Serving it

Memory is stateful, so inference is a streaming job, not a batch one:

```
kafka(tx stream) ─▶ feature builder ─▶ TGN (memory in Redis) ─▶ score
                                              │
                                    async ▼ (every N events)
                              memory checkpoint ─▶ object store
```

Memory lives in Redis keyed by node id; a checkpoint every 10k events bounds
recovery time. Cold nodes fall back to their attribute embedding until they've
accumulated history.
