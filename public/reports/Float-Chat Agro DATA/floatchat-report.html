01

Executive Summary

FloatChat democratises access to oceanographic data. The international ARGO program deploys autonomous floats that cycle between the sea surface and 2,000 m depth, recording temperature, salinity, and pressure — but that data is locked in multi-dimensional NetCDF binaries that require specialised tools (Ocean Data View, MATLAB, xarray) to read.

FloatChat lets a researcher, climate analyst, or policy maker simply ask "What was the average salinity near Gujarat in winter 2023?" It answers by combining Retrieval-Augmented Generation, natural-language-to-SQL synthesis, a local NLP semantic parser, and an interactive dashboard — with a fully offline fallback so it never depends on paid cloud credits to function.

02

Why This Project

Oceanographic monitoring underpins climate research, monsoon forecasting, marine-ecosystem preservation, and maritime navigation. Yet accessing ARGO data presents three obstacles:

  • Complex binary formats — data lives in multi-dimensional NetCDF (.nc) files following CF metadata conventions.
  • Steep technical barrier — analysis requires Ocean Data View, MATLAB, or Python xarray / netcdf4.
  • Disconnected search — non-technical users cannot ask natural-language questions across depth, region, and season.
Design goal

Make deep-sea data universally queryable in plain language, with mathematical precision and full auditability — and keep it working when the cloud is unavailable.

03

Three-Tier Decoupled Architecture

A React dashboard talks to a Flask reverse proxy, which routes each query to one of two intelligence engines — a cloud FastAPI backend or a local Flask fallback — both of which resolve against the same PostgreSQL + PostGIS store of 255,000+ profiles.

04

Dual RAG Engine

Path A — Online Cloud RAG
  • FastAPI drives LangChain's SQL Database Agent with OpenAI gpt-3.5-turbo.
  • The agent inspects live database schemas and generates structured SQL.
  • ChromaDB retrieves relevant oceanographic domain metadata for context.
Path B — Offline Local RAG / Fallback
  • main_local.py / smart_query.py run with no external API.
  • SentenceTransformer (all-MiniLM-L6-v2) embeddings + spatio-temporal regex parsing.
  • Maps regions, seasons, and measurement types directly into parameterised SQL.

Processing workflow

  1. Query submission — the user types a natural-language question in the React chat interface.
  2. Dual-path processing — the router picks the cloud agent or the local engine based on configuration and API-key availability.
  3. Execution & synthesis — the database returns numerical results; the engine formats a natural-language response with metadata and the underlying SQL shown for scientific auditability.
05

Data Pipeline & Schema

The ETL pipeline (etl_final.py, load_all_incois_data.py) ingests multi-dimensional .nc files, decodes Julian timestamps, flattens depth profiles, normalises coordinates, and bulk-inserts into the profiles table.

[NetCDF (.nc) files]
       │
       ▼  xarray extraction: platform ID, lat, lon, time, pressure, temp, salinity
       ▼  data cleaning: timezone normalization, NaN filtering, QC checks
       ▼  flattening: 2-D arrays (time × depth) → 1-D relational rows
       ▼  batch insertion via SQLAlchemy Core (BATCH_SIZE = 50)
[PostgreSQL `profiles` table]

PostgreSQL schema — profiles

CREATE TABLE IF NOT EXISTS profiles (
    id             SERIAL PRIMARY KEY,
    filename       VARCHAR(255),
    float_id       VARCHAR(50),
    profile_index  INTEGER,
    depth_index    INTEGER,
    timestamp      TIMESTAMP,
    latitude       DOUBLE PRECISION,
    longitude      DOUBLE PRECISION,
    pressure       DOUBLE PRECISION,
    temperature    DOUBLE PRECISION,
    salinity       DOUBLE PRECISION,
    created_at     TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_profiles_float_id   ON profiles(float_id);
CREATE INDEX idx_profiles_timestamp  ON profiles(timestamp);
CREATE INDEX idx_profiles_location   ON profiles(latitude, longitude);
CREATE INDEX idx_profiles_filename   ON profiles(filename);

Spatio-Temporal Intelligent Querying

Named regions
Gujarat, Arabian Sea, Bay of Bengal, Indian Ocean, Chennai, Mumbai — resolved to SQL BETWEEN latitude / longitude clauses.
Seasonal timeframes
Winter, Monsoon, Summer, Spring, Autumn — plus specific calendar years 2015–2025.
Depth resolution
Surface layer (0–10 m), shallow profiles (0–50 m), and deep-sea levels down to 2,060 m.

Query and SQL transparency: the generated SQL is displayed alongside the conversational answer so every result is scientifically auditable.

09

Key Design Decisions

Hybrid dual-engine RAG
Rather than depend solely on paid cloud LLMs, a deterministic rule-based SQL generator and local transformer fallback keep the system available with no credits or connectivity.
Decoupled frontend proxy
The Flask frontend proxies backend microservices — no CORS issues, and backends can be swapped without touching UI code.
Direct SQL over vector chunking
Numerical time-series needs exact AVG / MIN / MAX. Generating SQL over a relational DB prevents LLM math hallucination; ChromaDB handles semantic metadata search.
Spatial bounding-box indexing
Pre-defined oceanographic coordinate boxes plus composite B-tree indexes give sub-second spatio-temporal lookups over hundreds of thousands of rows.
Chunked ingestion
BATCH_SIZE = 50 with periodic commits and explicit dataset closing handles tens of thousands of NetCDF files without Python memory exhaustion.
