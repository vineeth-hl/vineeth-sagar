01

Executive Summary

Zero-Day is a six-layer security framework for detecting and mitigating zero-day attacks in Kubernetes clusters. Because zero-day exploits have no known signature, the system abandons rule matching entirely and instead learns the normal shape of container behaviour — who talks to whom, on what ports, with what volume, in what sequence — then flags deviations in real time.

It ingests multi-source telemetry (audit logs, network flows, eBPF syscalls), builds overlapping temporal graph windows, scores them with a four-model ensemble anchored by a Temporal Graph Neural Network, attaches an explainable reason to every alert, and routes high-confidence detections to a Kubernetes-native containment operator that acts only after a human approval token is supplied.

Why This Project — The Zero-Day Problem

In cloud-native environments, Kubernetes clusters are under constant threat, and the most dangerous threats are the ones with no patch and no signature. Without an intelligent detection system, teams face five compounding failures:

  • Invisible attacks — container breakouts and supply-chain compromises are virtually undetectable by static rules.
  • Delayed response — breaches go unnoticed for weeks, allowing lateral movement across the cluster (MITRE ATT&CK T1021).
  • Blast radius — a compromised pod escalates privileges (T1548), reads secrets, and spreads before anyone intervenes.
  • Operational blindness — thousands of flows, syscalls, and audit events per second with no way to separate normal from malicious.
  • No explainability — even when an anomaly fires, SOC teams cannot see why, producing alert fatigue.
Design goal

Detect unknown attacks from behaviour alone, explain each decision to an analyst, and contain the threat automatically — while keeping a human in the loop for every enforcement action.

Six-Layer System Architecture

The system separates concerns into six independently deployable layers. Docker Compose orchestrates the local proof-of-concept; Helm charts and Kubernetes manifests handle production. A single telemetry event travels the full path below.

Architecture highlights

  • Dual-mode operation — file-based JSONL PoC (no Kafka needed) or full Strimzi Kafka production ingestion.
  • MITRE ATT&CK mapping — attack playbooks tied to T1610, T1548, T1021, T1041, T1059.
  • Multi-tenant SaaS — usage metering, billing, and namespace isolation across four subscription tiers.

Temporal Graph Construction Engine

The Graph Builder service converts raw telemetry into temporal graph windows suitable for ML processing.

FeatureDetail
SessionizationGroups events by container_id, pod_name, and 5-tuple network flows
Sliding windows60-second windows with a 30-second step — overlapping, so an attack straddling a boundary still appears whole
Graph structureNetworkX directed graphs with node and edge feature vectors
Output formatApache Parquet via the fastparquet engine (no C-extension conflicts in containers)
Dual modeFile-based JSONL input (local) or Kafka consumer (production)
Auto-flushBackground flusher wakes every step seconds; generates synthetic fallback events when real traffic is quiet

Input event schema

{
  "timestamp": 1704282000,
  "event_type": "network_flow",
  "src_pod": "frontend-abc123",
  "dst_pod": "backend-xyz789",
  "src_ip": "10.0.1.5",
  "dst_ip": "10.0.2.15",
  "dst_port": 8080,
  "bytes_out": 1024,
  "bytes_in": 2048
}

Window outputs

  • window_<ts>.nodes.parquet — pod_name, namespace, total_bytes, outgoing_unique_dst, flow_count
  • window_<ts>.edges.parquet — src→dst pairs with cumulative bytes and flow count
# File mode (local PoC)
python -m graph_builder.main file --input-file events.jsonl \
  --out-dir ./graphs --window-size 60 --step 30

# Kafka mode (production)
python -m graph_builder.main kafka --topic telemetry.logs \
  --servers kafka:9092 --out-dir /data/graphs

5.1 TGNN architecture deep dive

INPUT: Parquet window files
├─ nodes: (pod_name, cpu, memory, network_in, network_out, syscall_count) → 6-D
└─ edges: (flow_count, bytes_in, bytes_out, latency, duration)             → 5-D

NODE ENCODER (MLP)
└─ Linear(6, 64) → ReLU → Linear(64, 32)     → 32-D embedding per node

EDGE ENCODER (with temporal encoding)
├─ Sinusoidal positional time encoding (64-D)
│    PE(t, 2k)   = sin(t / 10000^(2k/d))
│    PE(t, 2k+1) = cos(t / 10000^(2k/d))
├─ concat [edge_features(5-D), time_encoding(64-D)] = 69-D
└─ MLP projection                            → 16-D edge embedding

ATTENTION LAYERS (Graph Attention, 4 heads)
├─ Head 1: port-based communication patterns
├─ Head 2: volume-based anomalies (unusual byte counts)
├─ Head 3: temporal sequence anomalies (timing deviations)
├─ Head 4: unusual peer connections (lateral movement)
├─ attention[i→j] = softmax(LeakyReLU(wᵀ[hᵢ ‖ hⱼ]))
└─ output[i]      = σ(Σⱼ attention[i→j] · W · hⱼ)   → (num_nodes, 64)

DUAL ANOMALY SCORING HEADS
├─ Node head: Linear(64→32)→ReLU→Linear(32→8)→ReLU→Linear(8→1)→Sigmoid
├─ Edge head: Linear(192→64)→ReLU→Linear(64→16)→ReLU→Linear(16→1)→Sigmoid
└─ Composite: final = 0.6 · node_anomaly + 0.4 · edge_anomaly

Training strategy — contrastive triplet loss

ℒ(a, p, n) = max ( ‖f(a) − f(p)‖2 − ‖f(a) − f(n)‖2 + α,  0 ) anchor / positive drawn from benign windows, negative from attack windows · margin α

Feature standardisation (TGNN preprocessing)

xnorm = x − μσ + 10−6 per-feature mean and standard deviation, with an epsilon guard against zero variance
Best practice

Run the baseline models (Autoencoder, LSTM-AE) for speed and the TGNN for accuracy. If PyTorch Geometric is unavailable, a lightweight IsolationForest baseline acts as a final safety net.

Safe Automated Containment — Kubernetes Operator

The Containment Operator (Go + controller-runtime) watches for Containment custom resources and enforces policy behind multiple safety layers.

ActionMechanismRiskRollback
Isolate podDeny-all NetworkPolicy (empty ingress/egress)mediumDelete the NetworkPolicy
Evict podGraceful termination via Eviction API (30 s grace)highPod auto-restarts via its Deployment
Blackhole trafficIstio VirtualService, 100% fault delay (1000 s)lowDelete the VirtualService

Containment CRD — security.example.com/v1alpha1

spec:
  alertID: "alert-frontend-123"
  confidence: 0.92
  suggestedAction: "isolate_pod"   # isolate_pod | evict_pod | blackhole_traffic
  explanation: "Unusual outbound traffic pattern"
  dryRun: true
  approvalToken: ""
status:
  state: "pending"     # pending → approved → applied → failed
  appliedAction: ""
  result: ""

Operator reconciliation loop

Reconcile(ctx, req)
  ├── Fetch Containment CR
  ├── If State == "applied" || "failed"        → return (no-op)
  ├── If Confidence < 0.7                       → UpdateStatus("pending", "confidence_too_low")
  ├── If !DryRun && ApprovalToken == ""         → requeue every 30s ("awaiting_approval")
  └── Execute action
        ├── "isolate_pod"       → create deny-all NetworkPolicy
        ├── "evict_pod"         → delete pod, 30s GracePeriod
        └── "blackhole_traffic" → Istio VirtualService fault delay
        → UpdateStatus("applied", action)

Approval workflow

kubectl describe containment alert-frontend-123
kubectl patch containment alert-frontend-123 \
  -p '{"spec":{"approvalToken":"approved-by-analyst"}}'
kubectl get containment alert-frontend-123 -o json | jq '.status'

Key Design Decisions

Why a Temporal GNN?
Lateral movement lives in graph topology — pod1 suddenly reaching admin-pod4 on port 22 — not in any single metric. A TGNN models the relationships flat-feature models discard.
Why four models?
Autoencoder is fast but relationship-blind; LSTM-AE reads sequences; DeepLog reads logs; TGNN reads topology + time. Ensemble voting gives the best precision–recall trade-off.
Why a Kubernetes operator?
A CRD-based operator follows the reconciliation pattern — idempotent, retryable, and native to kubectl approval workflows. Far more reliable than scripts.
Why dry-run by default?
A false positive that auto-contains can outdamage the attack. dryRun: true plus an approval token ensures a human validates before enforcement.
Why Parquet + fastparquet?
Columnar, compressed, fast analytical reads. fastparquet avoids C-extension conflicts in containers; a PersistentVolume shares windows between writer and reader with no database.
Why dual-mode (file + Kafka)?
File mode demos the whole system with no Kafka, Zookeeper, or Strimzi. Kafka mode handles production throughput with 3-broker resilience.
