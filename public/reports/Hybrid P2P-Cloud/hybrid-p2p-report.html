01

Executive Summary

Every mainstream file-transfer service routes your file through a corporate server and stores it on infrastructure you do not control. This engine challenges that model: files stream directly between browsers over a WebRTC DataChannel whenever the network permits, so zero servers touch the data and zero copies exist anywhere.

Because peer-to-peer connections fail more often than they succeed in the real world — symmetric NATs, carrier-grade NATs, corporate firewalls — the system treats connectivity as a probability, not a guarantee. A 5-second race decides between direct P2P and a cloud fallback that streams the file through AWS S3 and then destroys it with a serverless "Nuke Protocol," backed by a 24-hour lifecycle failsafe.

Best case
Direct P2PLAN-like speeds, zero server contact, nothing stored
Worst case

02

Why This Project

The guiding question: what if file transfers could happen directly between browsers — no middleman, no storage, no trace? Pursuing it meant confronting WebRTC DataChannels, NAT traversal, STUN/TURN relays, and the reality that the internet is designed to prevent direct connections between devices.

The result is a system built around network connectivity as a probability:

  • Best case (P2P succeeds) — files stream directly at LAN-like speeds; no server sees the data.
  • Worst case (P2P fails) — the system silently pivots to S3 with a 1-hour presigned URL, then destroys the file via a Lambda nuke and a 24-hour lifecycle failsafe.
Philosophy

The most important code is not the happy path — it is the fallback logic. Every component has a failure mode, and the system's quality is defined by how gracefully it handles each one.

03

Microservices Architecture

Three independently deployable services sit behind a unified Nginx Ingress: a React SPA, a FastAPI backend, and a Node.js Socket.IO signaling relay. External dependencies are Redis (ephemeral presence), AWS S3 + Lambda (cloud fallback), and a self-hosted Coturn STUN/TURN server.

04

The 5-Second Race Algorithm

The heart of the system is the useHybridTransfer hook. Instead of waiting indefinitely for WebRTC to negotiate, it runs an aggressive race between the P2P connection and a 5-second countdown.

startTransfer(file)
  │
  ├─ state: p2p_pending  → connectAndOffer()  → start 5 s countdown
  │
  ├─ P2P connected before 5 s ─────┐        ┌──── timer expires (5 s)
  │                                ▼        ▼
  │                          state: p2p_active   state: cloud_active
  │                                │                  │
  │                    sendFile() via DataChannel   POST /api/upload
  │                       (16 KB chunks)            (5 MB S3 multipart)
  │                                │                  │
  │                                └────► state: completed ◄────┘
Why 5 seconds?

WebRTC ICE negotiation completes in 1–3 seconds on open networks. A 5-second window gives STUN enough time to probe, but does not leave the user staring at a spinner when they are behind a corporate firewall that will never allow P2P. The user sees only a badge change: P2P Direct → Cloud Server Relay.

05

Zero-RAM Chunk Buffering with IndexedDB

Traditional receivers accumulate incoming chunks in a JavaScript array — a 500 MB file then consumes 500 MB of tab RAM and crashes on mobile. This engine writes every incoming 16 KB DataChannel chunk directly to IndexedDB (the TransferCache object store), bypassing RAM entirely.

The browser's IndexedDB implementation persists to disk (typically LevelDB), so memory usage stays flat regardless of file size. Only at the final step does the receiver read all chunks back, assemble a Blob, and trigger the download. This is the difference between "transfers files up to 50 MB" and "transfers files of arbitrary size."

Backpressure
Sender pauses when bufferedAmount exceeds the 64 KB bufferedAmountLowThreshold, resuming via onbufferedamountlow — natural flow control that adapts to network speed.
Chunk size
16 KB sits well below the SCTP ~64 KB fragmentation boundary while minimising per-chunk overhead — the reliability/speed sweet spot.
06

Burn-After-Reading Data Destruction

Cloud-relayed files are protected by a three-layer destruction cascade. Even if the user never triggers the Nuke Protocol, the file cannot exist beyond 24 hours — AWS enforces this at the infrastructure level.

LayerMechanismTriggerLatency
1abort_multipart_uploadUpload failure mid-streamImmediate
2AWS Lambda "Nuke Protocol" (head_object → delete_object)Post-download deletion requestSeconds
3S3 lifecycle policy24-hour automatic expiration≤ 24 hours

Graceful degradation at every layer

  • Redis unavailable? → async InMemoryStore with asyncio.Lock and manual TTL eviction.
  • WebRTC blocked? → 5-second timer triggers the S3 relay.
  • S3 upload fails mid-stream? → abort_multipart_upload cleans up orphaned parts.
  • Container crashes? → Kubernetes restarts the pod with resource limits preventing OOM cascade.

08

End-to-End Transfer Flow

From anonymous session creation through lobby discovery, SDP exchange, and either a direct DataChannel transfer or the cloud fallback.

1  Alice → POST /api/auth/join {"anonymous_name": "Hacker_4821"}
2  Auth  → JWT token (UUID + name + 2 h expiry)
3  Alice → POST /api/heartbeat  (every 30 s)  → SETEX user_online:{uuid} 60
4  Bob   → GET  /api/users/online             → [{user_id, name}]   (Alice visible)
   ── Bob selects Alice from the lobby ──
5  Alice, Bob → emit('register', {uuid})      → Socket.IO userSocketMap
6  Alice → emit('offer',  {targetUuid, sdp})  → relayed to Bob
7  Bob   → emit('answer', {targetUuid, sdp})  → relayed to Alice
8  both  → emit('ice-candidate', …)           → trickled both ways

   ┌─ P2P succeeds (< 5 s) ───────────────────────────────────────┐
   │  DataChannel: JSON metadata {filename, size, type}           │
   │  DataChannel: binary chunks (16 KB)  → Bob writes IndexedDB  │
   │  Bob assembles Blob → triggers download                      │
   └─────────────────────────────────────────────────────────────┘
   ┌─ P2P fails (5 s timeout) ───────────────────────────────────┐
   │  Alice → POST /api/upload  (5 MB multipart stream to S3)    │
   │  S3    → 1-hour presigned URL → shared with Bob             │
   │  Bob   → downloads → triggers Lambda Nuke → S3 delete_object │
   └────────────────────────────────────────────────────────────┘
Signaling is a pure relay

Once ICE completes and the DataChannel opens, the signaling server is no longer involved. It never inspects or stores file data — only SDP offers/answers and ICE candidates.

Data Storage Schema

Redis presence store

Key pattern:   user_online:{uuid}
Value:         "{anonymous_name}"        e.g. "Hacker_4821"
TTL:           60 seconds
Heartbeat:     every 30 seconds (POST /api/heartbeat)
Scan method:   SCAN (non-blocking) + batched MGET

S3 object layout

Path:          uploads/{user_id}/{uuid4}.{extension}
Metadata:      {"sender_uuid": "{user_id}"}
Presigned URL: GET, expires in 3600 seconds (1 hour)
Lifecycle:     Expiration after 1 day
Multipart:     AbortIncompleteMultipartUpload after 1 day

IndexedDB (browser-side)

Database:      TransferCache
Object store:  chunks
Data:          raw binary ArrayBuffer (16 KB per entry)
Lifecycle:     cleared after Blob assembly and download trigger

Security Architecture

Authentication flow

Client                                  Server
  │  POST /api/auth/join {"anonymous_name": "X"}
  │ ─────────────────────────────────────►  generate UUID4
  │                                         sign JWT (HS256): sub=uuid, name=X, exp=+2h
  │  ◄─────────────────────────────────────  {"access_token": "eyJ..."}
  │  POST /api/heartbeat  Authorization: Bearer eyJ...
  │ ─────────────────────────────────────►  decode + verify HS256 + check exp
  │                                         SETEX user_online:{uuid} 60
  │  ◄─────────────────────────────────────  200 OK

Container security posture

  • Non-root execution across all containers (appuser:appgroup, nginx:nginx).
  • Multi-stage builds strip Node.js, npm, and pip from production images.
  • Kubernetes resource limits — API 500m / 512Mi, frontend 200m / 128Mi, signaling 250m / 256Mi.
  • AWS IAM least-privilege — the Lambda holds only s3:DeleteObject and s3:GetObject.
  • No persistent credentials in containers — secrets injected via Kubernetes Secret objects.
12

Key Design Decisions

16 KB DataChannel chunks
SCTP fragments messages crossing the ~64 KB boundary, destroying throughput. 16 KB stays well below it while minimising per-chunk overhead.
Redis ephemeral keys, not a DB
Presence is temporal. SETEX with a 60 s TTL means a crashed client's key simply evaporates — no cleanup jobs, no phantom users. 30 s heartbeat gives a 2× margin.
SCAN, not KEYS *
Redis is single-threaded; KEYS * blocks the whole keyspace. SCAN returns cursor-based pages and stays responsive at thousands of keys.
In-memory Redis fallback
InMemoryStore mirrors the async Redis API with asyncio.Lock and manual TTL, so python start.py runs with zero external dependencies.
aioboto3, not boto3
Synchronous boto3 blocks the event loop during uploads, serialising every transfer. aioboto3 wraps operations in async context managers for true concurrency.
Split Ingress resources
Nginx regex rewrite annotations apply to every path in an Ingress. One Ingress for /api rewrites, one without for / and /socket.io, prevents breaking static-asset paths.
Host networking for Coturn
TURN relay needs dynamic UDP ports across 49152–65535. Docker bridge NAT cannot handle that scale efficiently; host networking gives Coturn the raw stack.
IndexedDB, not in-memory arrays
A JS array of 500 MB of ArrayBuffers pushes the tab past 500 MB RAM. IndexedDB writes to disk, keeping RAM flat for arbitrary file sizes.

Challenges Faced & Solutions

#ProblemSolution
1Symmetric NAT — P2P worked on home networks but failed 100% on mobile data and corporate networksSelf-hosted Coturn TURN with host networking to relay encrypted media, plus the 5-second race so users never wait on a connection that will never form
2Railway dynamic $PORT — hardcoded --port 8000 made the container unreachable behind the proxyentrypoint.sh reads $PORT at runtime: exec uvicorn app.main:app --host 0.0.0.0 --port "${PORT:-8000}"
3Redis blocking the event loop — eager pool init at import time hung the whole FastAPI startup if Redis was slowLazy Redis init wrapped in the InMemoryStore fallback — connection attempted on first use, transparent takeover on failure
4Browser RAM exhaustion — a 200 MB file in a JS array killed the tab on mobileIndexedDB chunk buffering — each 16 KB chunk written straight to TransferCache; RAM stays constant
5DataChannel buffer overflow — sending as fast as FileReader reads silently dropped chunksBackpressure via bufferedAmountLowThreshold (64 KB) with pause/resume on onbufferedamountlow
6Nginx regex vs SPA routing — a single Ingress rewrote static assets to 404Two separate Ingress resources — one for /api rewrites, one for / and /socket.io
7Orphaned S3 multipart uploads — partial uploads persisted, accruing costThree-layer cleanup: immediate abort_multipart_upload, a 1-day lifecycle rule, and an on-demand Lambda
